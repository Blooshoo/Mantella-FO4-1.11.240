## Only genuinely new high/medium defect

**R2-01 — medium: cooperative cancellation can exhaust all workers and stall the next conversation.** N/port240/http/plugin/F4SE_HTTP240.cpp:51-53,70,82-99 fixes pool at four synchronous workers; N/port240/http/plugin/transport_winhttp.cpp:31,50,70-75 leaves a blocked receive occupied for up to its 180-second inactivity timeout despite cancellation. Four quickly superseded requests whose server accepts but withholds response headers occupy all four workers; a fifth valid conversation stays queued until a stale call returns. Epoch checks prevent wrong replies, not worker starvation. This is introduced by replacing cross-thread interruption with cooperative cancellation; doubling the finite pool postpones rather than prevents exhaustion. No Windows crash or measured in-game stall is claimed.

Repro to add (not executed): deterministic transport shim blocks four workers inside ReceiveResponse; cross four lifecycle boundaries and enqueue fifth; assert it starts within the new-conversation latency budget without releasing old barriers. Current scheduling cannot satisfy that assertion. Existing portable tests do not instantiate Workers or WinHTTP. Use a supported interruptible/asynchronous owner model, or an explicitly bounded cancellation-aware scheduling design; merely adding more workers cannot prove availability.

README N/port240/http/README.md:68-71 correctly states cooperative timeout and boundary limits, but **“4 workers so stale blocked requests cannot starve a new conversation” is false**. This availability guarantee should be removed even if runtime work is deferred. It is not an unavoidable Windows-only unknown: the fixed-pool counterexample follows from source.
